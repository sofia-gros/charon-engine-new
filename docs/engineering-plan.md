# 合意事項と現在地

会話の全記録ではなく、作業を再開するための正本。下記の設計方針は実装済みを意味しない。

## 目的と対象
- サークルの複数作品で使うRust製2Dゲーム基盤。シングルプレイ優先。
- 想定はマルフーシャ、Terraria、Noita、司令、オークの大群です等。ノベルも組み合わせで作れる拡張性を目指す。
- 開発はCodex Cloud/Linux。最初の実行・性能評価先はWindows 11。
- 基準PC: Ryzen 7 2700、RAM32 GB、M.2、RTX 4060 8 GB、143/144 Hzモニター。最低動作環境は未決定。
- 目標: 1920×1080描画144 FPS、セルシミュレーション60 Hz、CPUマルチスレッド、GPUシェーダー対応。
- 表示画素・シミュレーションセル・ブロックは別単位。セルの細かさは調整可能にし、密度ごとの負荷を測る。

## 設計方針
- 共通基盤は入力・時間・アセット・音声・描画・タスク実行・計測を提供する。砂の世界を必須にしない。
- Sand、破壊、物理、UI/文章等は選べる機能。Sandbox/Novel/横スクロールはその組み合わせとして構成する。
- 初期のpluginはRustでビルド時に登録する案。外部コードの動的ロードや公開APIの長期互換性は未決定。
- 各機能がデータを所有し、必要な問い合わせ・生成要求・描画・保存処理を公開する。全データ形式を同一にしない。
- 破壊表現は、積もるセル、回転する剛体、軽量な演出粒子を使い分け・併用する。
- 足場・弾の遮蔽・反応等を素材/作品で選べるようにする。演出専用粒子とゲームに影響する物質は区別する。
- 変換時の消失・二重生成を防ぐ。処理落ちを隠すため、ゲームに影響する物質を黙って演出へ変更しない。
- 砂/水は活動領域だけ更新し、安定領域は休止。地形変更・隣接移動・反応等で境界を越えて再起床する。
- 物質更新・反応・見た目のアニメーションは別。海の水域集約等は将来の候補で、最初から方式を固定しない。
- 描画/入力と固定tickのシミュレーションを分離。完了済みの不変状態を受け渡し、途中状態や変更通知を取りこぼさない。
- 製品のCPU並列実行を早期に検証する。単一スレッド版は比較の基準として使い、製品経路を1スレッドに固定しない。
- 同一移動先等の競合を解決し、スレッド到着順に結果を依存させない。セル1個をECSエンティティにしない。
- coreはGPUなしでも検証可能にする。wgpuを描画の第一候補とし、GPUシミュレーションcomputeの採否は別に判断する。
- Rustは特定版への固定を避けたいというユーザー希望。stable利用、実バージョン記録、依存lock、更新を機能変更と分離する方針。

## 開発と受け渡し
- engine/plugin/制作ツール/サンプルはGitHub管理が必須。まず一つのCargo workspaceにまとめる案。
- ユーザーは仕事で約10時間不在。即時の実機確認を前提にせず、自動検証と実機確認待ちを区別して進める。
- 最初の節目は、Windowsで入力から少量の砂の変化が見え、shader描画・別スレッドの固定tick・性能表示がある小サンプル。
- 最初の画面確認を後回しにしない。確認待ちの間に剛体や大量機能を積み増さず、独立した検証・整備を進める。
- 砂を使わない小さな画面も早期に試し、共通基盤へ砂の都合が混ざっていないか確認する。
- 実機用の起動/結果記録を簡単にし、確認済みの版へ戻れる状態を残す。GitHubの配布/CI手順はこれから整備する。
- テストは変更に応じて選択。保存則、競合、境界、休止/起床、表示反映、保存復元などの契約を守る。
- seed/入力列の再生、コマ送り、状態検査、性能の内訳を用意する。再現→原因特定→修正→回帰確認で進める。
- 活動領域版と全領域版、並列版と基準版を小シーンで比較。実際のテスト件数と未実施項目を報告する。
- CPU計算・GPU描画・転送/同期・フレーム間隔・tick遅延を分ける。多スレッドというだけで高速と判定しない。
- 全テスト反復や巨大な先行設計で時間/利用枠を浪費しない。小さく動く変更と必要な検証を優先する。

## 現在地と次の一手
- 実装: std実行基盤、wgpu/winit描画基盤、砂/会話plugin、2サンプルをCargo workspaceに分離。共通基盤は砂に依存しない。
- 描画/入力と60 Hz更新は別スレッド。砂はワーカー数CLI指定、移動提案をRayonで並列化し、競合適用は所有者が行う。
- 移動は32×32の活動領域のみ。休止/境界再起床に対応。RGBA生成/転送は全セルのまま。大規模世界対応済みとは扱わない。
- CPU検証8件: 実行基盤1、砂6、会話1。保存則/移動競合/休止再起床/部分タイル境界/seed入力列を全走査基準と比較。1/2/4ワーカーを対象にする。
- 計測は4シーン×2密度×3ワーカーの24条件。更新と画像生成の内訳、実使用ワーカー、最終状態hashを記録し、ワーカー間の結果一致を確認。
- 共有クラウドの960×540崩落は4workerでp95約5.40ms/最大16.16ms。1/2workerでは最大tickが16.67msを超える試行あり。実機性能保証ではない。
- CPU計測の再実行はscripts/measure.py。条件/ソースhash付きCSV/JSONはdocs/benchmarks/。静止時の全セル画像生成、競合処理の直列部分が今後の改善対象。
- Linux SwiftShaderでフルHD shader出力全2,073,600画素を照合。共通描画を使う砂/会話の実ウィンドウもXorg dummy+llvmpipeで検証。
- Linux実入力のMP4/GIF/PNG・状態CSVはdocs/media/、入口はusage.md。砂は追加/壁/穴開け/リセット、会話は2分岐/再開/終了を対象にする。
- Windows MSVCターゲットのcargo checkは両サンプルで成功。Windows実機操作、ハードウェアGPU、144 FPS達成は未検証。クラウドCPU値で代用しない。
- Rust stable、Cargo.lock管理。初回導入/ツール更新はsetup、日常は既存ビルドを再利用。操作と検証方法はdocs/usage.md。
- Windows用PowerShell起動/記録とLinux/Windows CI定義あり。GitHub CIの成功は未確認。APIはネットワーク拒否で、PR作成は未完了。
- GitHub開発ブランチはcodex/engine-bootstrap。main未統合。API許可追加は環境設定の下書きへ保存済み、適用未確認。
- 次は画像生成/転送の差分化を小さく実装し、今回の同一負荷と状態比較で効果と正しさを検証する。剛体/液体の大量追加を先行させない。
